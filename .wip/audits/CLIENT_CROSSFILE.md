## 1. from lane branch fix/modules

Integration notes beyond CONTRACT.md for the morale/jurisdiction rework (client/morale.lua, client/jurisdiction.lua as implemented on fix/modules). (1) FenixMorale.release(vehNetID, 'jurisdiction') is called ONLY by client.lua's gradual handoff. jurisdiction.lua never releases units (it can't see spawnedVehicles); FenixJurisdiction.checkCrossing just returns from,to for a confirmed different-agency crossing and makes the radio call itself. Delete the old block in maintainPoliceUnits that loops spawnedVehicles calling FenixMorale.beginRetreat(..., 'jurisdiction'). (2) FenixMorale.isRetreating(id) is also true for RELEASED units, so check FenixMorale.isReleased(id) first for the delete path. (3) In handleChaseBehavior, skip handleFootChase (and any other early per-unit tasking such as the ticket/surrender approach pickers, if they choose an officer from that unit) while FenixMorale.isRetreating(vehNetID) is true. Otherwise client.lua keeps tasking, or newly commits, a foot chaser from a retreating/released unit and fights morale.lua for the same ped. Release any breach shield that unit's chaser holds. (4) When a unit goes from FenixMorale.isRetreating == true last cycle to false now (it rejoined after regrouping), set every entry in vehicleData.officerTasks to nil (calling releaseBreachShield for any 'FootChase'/'FootCombat' entry first). The ground loop only re-tasks on a marker change, so a driver whose marker still reads 'VehicleChase' keeps morale.lua's TaskVehicleDriveWander forever and never rejoins the chase. Track the previous state in vehicleData (e.g. vehicleData.wasRetreating). (5) FenixMorale.assess already records deaths it sees in liveOfficers, so calling FenixMorale.reportDeath next to reportOfficerDown is safe and idempotent. FenixMorale.officerRemoved(vehNetID, pedNetID) should be called at the foot-chase give-up (handleFootChase, `dist > giveUpDistance`) and in handleFarPeds' ground loop, before or after removing the officer from vehicleData.officers. (6) FenixPursuit.announceBackupRequest now takes an optional kind ('officerDown'|'takingFire'); FenixBackup.maybeAnnounce passes it, so client.lua needs no change.

## 2. from lane branch fix/server

Server contract on fix/server (server/server.lua). (a) spawnPoliceHeliNet/spawnPoliceAirNet ignore their 4th argument (spawnTable); the server derives polHelis/milHelis/milPlanes from the player's vehicle exactly as maintainPoliceUnits does, so you may stop sending it. Both now ALWAYS reply with spawnPoliceHeliNetResponse/spawnPoliceAirNetResponse, (nil, nil) on any failure. That includes an immediate nil when no air unit is configured for the wanted level: maxHeliUnitsPerLevel[2]=1 but polHelis starts at 3 stars, so at 2 stars the current loop sends one request per second and gets nil back each time. Add a per-type backoff after a nil reply, e.g. skip heli and air requests for 10 s. (b) In the spawnPoliceHeliNetResponse/spawnPoliceAirNetResponse handlers, do not pre-set officerTasks[pedNetID] to 'HeliChase'/'PlaneChase'/'CombatPed'. The server sends its initial task to the ped's network owner, or to the requester while no client owns it yet, and it is lost if the requester isn't the owner when it lands. Leave the status nil so handleHeliChaseBehavior/handleAirChaseBehavior issue TaskHeliChase/TaskPlaneChase/TaskCombatPed themselves on their first pass. (c) fenix-police:updateWantedStatus may be sent only on change plus a 10-15 s heartbeat (limit 120/min shared with aftermathState). The server broadcasts fenix-police:cleanupAllPolice once per someone->nobody-wanted transition, per player, skipping players with a synced wanted level or an aftermath hold. (d) fenix-police:server:issueTicket is limited to 3/min. It is refused with ticketIssued(0, true), i.e. a warning, unless the player is wanted and one of their own officers is within TicketSystem.windowDistance+6 m of their ped. Send it after the citation writing loop and treat (0, true) as a warning. (e) fenix-police:server:fieldRevive requires aftermathState(true) to have been sent, one of the player's own officers within Config.Aftermath.reviveRange+6 m of the player's ped, and Config.Security.fieldReviveCooldown (300 s). Keep sending it BEFORE endAftermath()'s aftermathState(false).

## 3. from lane branch fix/ambient

Config.Driving (config.lua) documents that a single { min, max } pair applies at every wanted level, but client.lua's officerDrivingProfile does randRange(levelValue(c.aggression, wantedLevel, nil), 0.4, 1.0). levelValue returns tbl[wantedLevel], which for a single pair like { 0.10, 0.25 } is a bare number (or nil above level 2), and randRange then does `range[1]` on a number: 'attempt to index a number value', inside the ground-unit loop. Same for c.ability. Fix in levelValue (or a sibling used for ranges): if type(tbl) == 'table' and type(tbl[1]) == 'number' and type(tbl[2]) == 'number' then return tbl end before indexing by level, and have randRange ignore any range that is not a table (`if type(range) ~= 'table' then range = nil end`).

## 7. from lane branch review/server

Send TriggerServerEvent('fenix-police:server:issueTicket', level) after the citation-writing loop in triggerTicket, not before it. When it arrives, the server requires the player to still be wanted and one of their own officers to be within (TicketSystem.windowDistance or 3.5) + 6 m. It is rate limited to 3 per minute and otherwise replies ticketIssued(0, true). Since pendingTicket is read right after the loop, wait briefly, about 2 s, for the reply. Optionally switch updateWantedStatus to change-only plus a 10-15 s heartbeat; the server tolerates both.
